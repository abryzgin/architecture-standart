## **Функциональные требования** (use-cases верхнего уровня)

| № | Действующие лица / системы | Use Case | Шаги / краткое описание |
|:-:|----------------------------|----------|--------------------------|
| 1 | **Гость сайта** | Просмотреть линейку депозитов | 1. Запрос HTTPS→ Website API → Deposit-Catalog Service.<br>2. Каталог отдает актуальные ставки. |
| 2 | **Гость сайта** | Оставить заявку на депозит | 1. Форма «Ф. И. О.+телефон»<br>2. Website API отправляет событие **NewLead** в Integration Bus.<br>3. Call-center Platform создаёт обращение. |
| 3 | **Оператор КЦ** | Позвонить клиенту и уточнить детали | 1. Открывает карточку обращения.<br>2. Может назначить спец-ставку → событие **SpecialRateRequest**. |
| 4 | **Идентифицированный клиент (ИБ)** | Рассчитать персональную ставку | 1. Запрос UI → IB Backend.<br>2. IB вызывает **Rate Service** → кэш / АБС.<br>3. Возвращается персональная ставка. |
| 5 | **Идентифицированный клиент (ИБ)** | Подать заявку на депозит | 1. Указывает счёт и сумму.<br>2. Запрашивает SMS-OTP → **OTP Service** → SMS Gateway.<br>3. Вводит OTP, IB отправляет **DepositApplication** в Integration Bus. |
| 6 | **Бэк-офис депозитов** | Обработать заявку | 1. Получает задачу из Back-office UI.<br>2. При необходимости согласует ставку с кредитным аналитиком (в том же UI).<br>3. Подтверждает в **Deposit Gateway** → запись в АБС. |
| 7 | **Система** | Информировать клиента | 1. После записи в АБС Deposit Gateway публикует **DepositOpened**.<br>2. SMS Gateway отправляет уведомление. |

## **Нефункциональные и архитектурно-значимые требования (NFR)**

| № | Требование |
|:-:|------------|
| 1 | Доступность сервисов ≥ 99,9 % (R-1, R-2). |
| 2 | Отказоустойчивость через два ЦОД, горизонтальное масштабирование фронтов и микросервисов (R-1, R-2, S-4). |
| 3 | Время отклика UI ≤ 200 мс; генерация ставки ≤ 100 мс (U-2, P-1). |
| 4 | Все каналы шифруются TLS 1.2+, секреты в Vault (+R-2). |
| 5 | Интеграция каналов ↔ АБС только через **Integration Bus / API-Gateway**, без прямых вызовов (+R-1, +R-4). |
| 6 | Собственный **OTP Service** (HTTP+HSM) вместо доработки ядра ИБ (F-4). |
| 7 | Используем существующий техстек: Java 17 / Spring Boot, .NET 4.5 (ИБ), MS SQL / Oracle (S-3). |
| 8 | CI/CD-пайплайны, Swagger-документация (S-2, S-1). |
| 9 | Ограничение загрузки АБС — все запросы кэшируются, применяются circuit-breaker / throttling (+R-4). |

#### Ключевые компоненты и интеграции
| Компонент | Назначение | IT-команда-владелец |
|-----------|------------|---------------------|
| **Website BE/FE** | Публичный каталог, приём лидов | Web-team |
| **Интернет-банк** | Кабинет клиента; адаптируется для вызова новых REST API | Team Internet-bank |
| **API-Gateway / MQ** | Единая точка приёма запросов от каналов; публикация событий в очередь | DevOps / Integration-team |
| **Deposit Gateway** | Оркестрация заявки (saga), запись в АБС, публикация статусов | Transformation Core-team |
| **Rate Service** | Генерация/кэш ставок; обращается к АБС только чтением | Transformation Core-team |
| **OTP Service** | Отправка и проверка SMS-кодов | Infrastructure / Security |
| **Call-center Platform** | Приём лидов из очереди; UI для операторов | Call-center IT |
| **АБС** | Мастер-система депозитов | АБС-team |
| **SMS-Gateway** | Отправка SMS-уведомлений | Infra-team |

##### Логика выбора
* Асинхронная очередь защищает core от пикового трафика (NFR #5, #9).
* **Микросервисы** только вокруг депозита → низкая площадь изменений в унаследованных системах, соответствие S-3.
* **OTP Service»** экономит бюджет, убирает зависимость от подрядчика.
* **RabbitMQ** — быстрый старт для MVP; позже брокер заменяем/дополняем Kafka (FURPS +R-3).

##### Как удовлетворяются требования
* SLA 99,9 % — кластеры API-Gateway, RabbitMQ и Spring-Boot-MS развернуты в обоих ЦОД (NFR #1).
* Performance — кэш ставок (Redis) и read-only запросы к АБС дают ответ ≤ 100 мс (NFR #3).
* Security — весь трафик поверх TLS, секреты в HashiCorp Vault (NFR #4).
* Supportability — OpenAPI-контракты; CI/CD на GitLab с автотестами (NFR #8).

## **Альтернативы**

| Вариант | Плюсы | Минусы / прич. отказа |
|---------|-------|-----------------------|
| **Прямые REST-вызовы ИБ → АБС** | Быстрее реализовать | Ломает NFR #5, перегружает АБС, риски отказа Интернет-банка при падении АБС |
| Хранить ставки только в АБС, без Rate-Service | Нет дублирования данных | Нагрузка на АБС, медленный расчёт (< 1 с) → нарушает P-1 |
| Сделать функциональность депозитов прямо в ядре Интернет-банка | Не нужно новых MS | ASP.NET 4.5 монолит, тяжёлые релизы, нет горизонтального масштабирования, блокируется Kafka-стратегия |

## **Недостатки, ограничения, риски**

* **Технический долг ASP.NET 4.5** — обновление монолита остаётся трудоёмким.
* **Vertical-only АБС** — при лавинообразном росте он-лайн заявок возможен bottleneck; предусмотрен throttle, но риск остаётся.
* **RabbitMQ как временный брокер** — при переезде на Kafka требуется миграция конфигурации и клиентов.
* **OTP Service**: требуется HSM-интеграция и регуляторная сертификация — может сдвинуть сроки.
* **Командная загрузка**: Core Transformation team берёт новые MS + Gateway — нужен рост компетенций по DevOps и SRE.
* **Бизнес-риск**: ручная обработка в MVP (Use Case #6) может ухудшить восприятие быстроты сервиса; важно обозначить SLA на manual-шаг.
